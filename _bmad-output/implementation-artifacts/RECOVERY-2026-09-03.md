# Recovery: the seven garbled recordings

## What was wrong

Seven of sixteen recordings held a `system.wav` declaring 16 kHz whose real rate
was 8 kHz or 5333 Hz. The far end of each call transcribed into fluent invented
dialogue, and the title, tags and summary were derived from the fabrication.

Independently measured before anything was touched, by comparing each file's
sample count against the Session's wall clock:

| Recording | Input device | System ratio | Mic ratio |
| --- | --- | --- | --- |
| `20260901-093248-evi3` | (not recorded) | **2.01** | 1.00 |
| `20260901-094602-t89h` | (not recorded) | **2.00** | 1.00 |
| `20260901-140032-ooqn` | AirPods Pro | **2.01** | 1.00 |
| `20260902-093137-14ln` | AirPods Pro | **2.01** | 1.00 |
| `20260902-094645-sp3m` | AirPods Pro | **2.02** | 1.08 |
| `20260903-094601-madw` | Sony BT headset | **3.00** | 1.00 |
| `20260903-103103-y774` | Sony BT headset | **3.00** | 1.00 |

The nine correct recordings sat at 1.00–1.03. Every microphone stream was sound.

## What was done

**Nothing was resampled, re-encoded or deleted.** The samples were complete and
intact; only the header's claim about their rate was wrong. So the repair rewrote
four bytes per file — `sampleRate` and `byteRate` in the `fmt ` chunk — and the
app's own pipeline did the rest.

1. **Backed up** the seven `meeting.json` records and their seven notes, 324 KB, to
   `~/Library/Application Support/Minutes/recovery-backup-2026-09-03/`.
2. **Computed the true rate** as `declared / round(declared / observed)` — snapping
   to the integer factor rather than using the raw observation, because the wall
   clock includes the moments before the first sample arrived and after the last,
   which is why a true 8000 Hz measured as 7919–7996.
3. **Rewrote the headers**, recording the original rates in
   `recovery-backup-2026-09-03/rate-repair.json` so the change is reversible.
4. **Reset each `stage` to `captured`** and relaunched the app, so
   `Pipeline.resumeInterrupted()` re-ran them through the existing pipeline. No
   second transcription path was written.

No user-entered speaker name, exclusion or hand-edited title was at risk: all
seven had auto-assigned names, no exclusions, and auto-generated titles.

## What came back

Quantitatively, and **without quoting any of it** — a transcript is meeting
content and this repository is public (PRD §9.1). The guard added in Story 13.5
refused the first version of this file for exactly that reason, which is the
guard working.

| Recording | Utterances before → after | The far end |
| --- | --- | --- |
| 26-minute Teams call | 144 → **355** | opened mid-sentence on an unrelated word before; now opens on the subject the meeting was actually about |
| 11-minute Slack call | 45 → **136** | invented dialogue before; ordinary greetings and an agenda after |
| 11-minute German meeting | 103 → **139** | ungrammatical word salad before; grammatical German after |
| 11-minute Slack call | 192 → **243** | one place name was being heard as an unrelated English phrase; correct after |
| 8-minute call | 205 → **230** | fragmentary before; a coherent opening statement after |
| 17-minute call | 236 → **298** | fragmentary before; coherent after |
| 1-minute call | 18 → **21** | both short and noisy; see below |

The German meeting is the clearest single piece of evidence, because grammatical
correctness is checkable without knowing anything about the meeting: the before
text is not German that a person could have spoken, and the after text is.

The utterance counts alone tell most of the story. A stream played at two or three
times speed yields far fewer segments than the speech it contains, so the count
rising by 30–150% is the fabrication being replaced by what was said.

## Honest caveats

- **`sp3m` did not clearly improve.** A 63-second recording whose *microphone*
  ratio is also off (1.08), which no other recording shows. Both transcripts are
  short and poor. It was repaired on the same evidence as the others and its
  system ratio is now 1.01, but nobody should claim its content is recovered.
- **Titles are still weak.** "Don", "What" and a date now, where before there were
  "New", "Sorry" and "Put The Fashion". They are generated by the keyphrase
  backend because no summarisation backend is enabled on this machine — a separate
  and pre-existing weakness. What changed is that they are now derived from real
  speech rather than from fabrication.
- **The transcripts are what the current model produces**, not a ceiling. A better
  model over the same repaired audio would do better.
- **The mechanism is inferred, not proven.** The correlation with a Bluetooth input
  device is 7 of 7, the located code path is consistent with all three observed
  ratios, and none of that is a proof against Apple's source. The guard built in
  increment 8 therefore rests on the *observable* — a sample count that disagrees
  with the clock — which holds even if the diagnosis is wrong.

## Verified afterwards

```
$ Minutes --check-rates
16 recording(s) checked, 0 failing
```

And the round trip was proven on real data rather than only on fixtures: one
repaired header was deliberately reverted, `--check-rates` reported
`FAIL … !system 16000/7919 Hz x2.02`, `--check-rates --repair` fixed it, and the
app re-transcribed it on relaunch. Library afterwards: 16 readable, 0 unreadable,
16 notes linked, 0 not found.

## If you ever want the originals back

`recovery-backup-2026-09-03/` holds the pre-recovery records and notes, and
`rate-repair.json` holds each file's original declared rate. Writing those rates
back into the headers reproduces the garbled state exactly — the audio was never
altered.
