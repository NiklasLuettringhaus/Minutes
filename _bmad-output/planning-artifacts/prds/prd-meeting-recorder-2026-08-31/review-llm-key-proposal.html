The LLM You Already Own

A review of gating summaries on a real language model, and paying for one with an API key.

Subject Minutes, increment 3 proposal Date 31 Aug 2026 Lenses adversarial, edge-case-hunter Findings 14 + 13 paths

Verdict · split the proposal

Half of this is clearly right and should ship on its own. The other half is the most expensive way to get what you want, and it breaks the product's founding claim to do it.

Gating the summary on a real model is a good instinct the PRD already argues for. But "gate the summary" and "buy the intelligence with an API key" are two independent decisions fused into one sentence. Separate them and the answer changes, because you are already holding an unused LLM.

The finding that should decide thisThe model is switched off, not absent

Apple's on-device model backend was built in increment 1 — story 7.1, FR-27 — is unit-tested, and is wired into the pipeline with guided generation into a typed structure. It has never run once. Here is why:

SystemLanguageModel.default.availability
  = unavailable(appleIntelligenceNotEnabled)

That reason is the whole point. It is not deviceNotEligible and not modelNotReady.

  • The machine is an Apple M5 MacBook Pro, 24 GB — comfortably eligible.
  • com.apple.CloudSubscriptionFeatures.optIn contains "opted_out_buddy" = 1 — Apple Intelligence was declined during Setup Assistant.

So the sequence was: the app shipped with an LLM backend; that backend checked availability at run time, correctly found the feature off, and fell back to keyphrase extraction exactly as designed; you read the keyphrase output, correctly judged it not worth having, and proposed buying a language model.

Switching on Apple Intelligence in System Settings gets you real LLM summaries with no new code, no key, no recurring cost, and nothing leaving the Mac. Do that before deciding anything else here.

Section 01Your judgement of the output is correct

The complaint is well-founded, and it pays to be precise about which part is bad. This is a real summary from your notes folder:

Okay, let's talk about the pricing page redesign. The preaching page is confusing customers, conversion dropped 12% last quarter. So we decided to simplify the pricing page down to three tiers. Can you also check the mobile pricing page layout?

That is not a summary. It is four sentences copied out of the transcript, in order, at roughly 80% of the transcript's own length — for a 30-second recording, nearly the whole thing. It also says preaching page, because Whisper misheard pricing page. That matters later.

The titles, by contrast, are fine: "Pricing Page", "Page Redesigned Together". So "better titles" solves a problem you do not have, while "summaries" solves one you do.

Section 02Adversarial findings

01NFR-1 and NFR-6 are contradicted, not amendedbreaks a claim
Where
PRD §8 — NFR-1, NFR-6
Problem
NFR-1 reads "No audio, Transcript, or Metadata is transmitted anywhere, ever." NFR-6 requires the zero-egress claim be "verifiable by an outside observer with a network monitor". A user-supplied key makes the app fail NFR-6 by construction — a network monitor will show transcripts leaving.
Fix
Either retire NFR-1 and NFR-6 explicitly, in writing, with the brief's thesis alongside them — or keep the model local. Do not leave them standing while shipping code that violates them.
If left
The product's strongest claim becomes false and stays written down as though it were true.
02The transcript is not yours alone to sendconsent
Where
proposal point 3
Problem
The payload is other people's speech — verbatim, named, timestamped and attributed. Your own company all-hands had 37 participants. None of them agreed to have their words sent to an API vendor.
Fix
If this ships, sending must be per-meeting and opt-in, with the participant list shown at the moment of sending. Never a global default that silently applies to every future meeting.
If left
One settings toggle exports every colleague's words from then on.
03This creates a company exposure, not just a personal preferencecompliance
Where
proposal point 3 · PRD §9.1
Problem
Voice, name and content together are personal data. Sending them to a US provider makes that provider a processor, which needs a legal basis and a data processing agreement. An individual employee cannot establish either on colleagues' behalf.
Fix
Default off, and say this plainly in the settings pane. Recommend the local path for work meetings. If the company already has an approved vendor under a DPA, use that one and name it.
If left
A personal productivity tool quietly becomes a data-protection problem with your employer's name on it.
04Two independent decisions are fused into one
Where
general
Problem
"Gate the summary on a real LLM" and "get the LLM by API key" are separable. The first is clearly right. The second is one of three ways to satisfy it, and the only one carrying these costs.
Fix
Decide them separately — see the options table below.
If left
Accepting the good half drags in the contentious half for no reason.
05FR-26 becomes unsatisfiable as written
Where
PRD §4.6 — FR-26
Problem
FR-26 requires every Meeting to receive a title, a tag set and a summary, and states no Meeting is ever left untitled. A basic tier with no summary contradicts it.
Fix
Amend FR-26 so summary and tags become conditional while the title guarantee survives. Also define "title setting" — a manual title, a heuristic title, or a filename template? The proposal says it without saying which.
If left
The PRD and the build disagree about whether a meeting can exist without a summary.
06"Better titles" targets the component that already works
Where
proposal point 3
Problem
Heuristic titles are adequate; heuristic summaries and tags are not. preaching-page as a tag is the visible failure, not Pricing Page as a title.
Fix
Scope the model to the summary, decisions, action items and tags. Leave title generation alone until it is measured against a real alternative.
If left
Recurring per-token spend regenerating output that was already fine.
07The quality ceiling is the transcript, not the summariserroot cause
Where
general
Problem
"Preaching page" is a Whisper error. An LLM will write a fluent, confident summary of the wrong words — and fluency makes the error harder to catch than the current clumsy extract does.
Fix
Before blaming summarisation, re-run a meeting with a stronger transcription model. large-v3-turbo is already downloaded and Parakeet is available. Compare word error rate on the same audio first.
If left
Money and egress spent on a problem whose cause is upstream, and the remaining errors get harder to notice.
08No cost model, against a PRD that names zero cost as a constraintbreaks a claim
Where
PRD §9.2
Problem
§9.2 states zero run-time cost is "a design constraint, not an outcome — it is what makes a tool with no business model sustainable." A 60-minute meeting is roughly 8–10k words: call it 12k tokens in. Several meetings a day is a real recurring bill.
Fix
Show an estimated token count and cost before sending, plus a running monthly total. And renegotiate §9.2 in writing rather than silently breaking it.
If left
Unbounded silent spend, and a stated constraint quietly abandoned.
09Key storage is unspecified, in an ad-hoc-signed appsecurity
Where
proposal point 3
Problem
An API key in UserDefaults is plain text readable by any process running as you. This app is ad-hoc signed with no stable identity, which weakens Keychain ACLs too.
Fix
Keychain only, kSecAttrAccessibleWhenUnlocked. Never UserDefaults, never the notes folder, never a log line, and never echoed back into the UI after saving.
If left
A credential leak out of a note-taking tool.
10Provenance stops being checkablehonesty
Where
PRD §4.6 FR-30, §9.3 · note frontmatter
Problem
Every note ends its frontmatter with generated_by: Minutes (local, on-device). With a cloud backend that line is false, and FR-30's promise that a reader can tell a model summary from keyphrase extraction now has three answers, not two.
Fix
Extend the backend kind with provider and model identifier, and make generated_by conditional per note. Old notes must keep saying what was true when they were written.
If left
Notes assert on-device generation regardless of what happened — and §9.3, the honesty section, is the thing that breaks.
11No offline or failure path is stated
Where
proposal point 3 · PRD §8 NFR-5
Problem
Meetings happen on planes, on captive-portal wifi, and on expired keys. NFR-5 requires that no failure path silently discards a note.
Fix
State it: on unreachable API, 401, 429, quota exhaustion or timeout, the note is still written with heuristic metadata and the failure is recorded on the meeting. Never block the note on a network call.
If left
A network error costs the user their meeting notes — the one outcome the whole app exists to prevent.
12"If we can actually use an LLM" needs a definition
Where
proposal point 1
Problem
"Can use" collapses three distinct states: no backend available at all, a backend configured but unreachable right now, and a backend working. Each needs different UI and a different fallback.
Fix
Define the gate as those three states explicitly before building the conditional summary.
If left
The gate gets implemented against whichever state the developer happened to think of.
13FR-52 shipped hours ago and this already contradicts it
Where
PRD §4.6 — FR-52
Problem
FR-52 gives a two-way choice: auto, or pin the deterministic backend. A third backend with a key makes it three-way with undefined precedence — Apple Intelligence on and a key present, which wins?
Fix
Define precedence before adding the option. The defensible order is explicit user pin, then local model, then cloud.
If left
Two settings that can disagree, and a summary whose origin depends on undocumented ordering.
14The basic tier is better than today, and the proposal undersells itin favour
Where
proposal points 1–2
Problem
§9.3 already requires that absence be represented honestly and never as invented content. An empty summary section is more compliant with the PRD than the current extract, which reads like a summary and is not one.
Fix
Ship the gate on its own merits, immediately, independent of any LLM decision. It improves the product today.
If left
A good change waits on an unrelated and much larger one.

Section 04Recommendation

Decision A

Gate the summary on a real model — accept

Ship it independently and soon. When no model is producing metadata, write the transcript, the heuristic title and the tags, and omit the summary, decisions and action items sections entirely rather than filling them with sentence extracts. §9.3 already asks for this. It makes the product more honest today, at no cost, whatever you decide about Decision B.

One amendment needed: FR-26 must be reworded so the title guarantee survives while the summary becomes conditional.

Section 05What to do before any of this

Re-transcribe one meeting with large-v3-turbo and compare it against the base output you have been reading. "Preaching page" is not a summarisation failure — and if the transcript is wrong, then every option in Decision B produces a confident, fluent, wrong summary. Fixing the input is cheaper than all three options and improves every one of them.
